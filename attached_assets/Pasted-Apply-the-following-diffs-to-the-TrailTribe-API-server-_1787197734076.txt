Apply the following diffs to the TrailTribe API server (artifacts/api-server). These fix a real overbooking race condition on volunteer task sign-ups, plus two N+1 query patterns in write-heavy paths.

Context/notes for the agent:
- volunteerTasks.ts: both the single-task signup endpoint (POST /events/:id/tasks/:taskId/signup) and the bulk-signup endpoint (POST /events/:id/tasks/bulk-signup) previously did a check-then-insert with no locking — two concurrent requests for the last open slot could both pass the capacity check and both succeed, overbooking the task beyond slotsNeeded. Fixed by wrapping the capacity check + insert in db.transaction() with .for("update") to lock the task row, serializing concurrent attempts on the same task. The bulk endpoint also had 3 unbatched sequential queries per taskId; now batches the task and existing-signup lookups into 2 queries total up front, keeping only the capacity-check-and-insert as a per-task locked transaction (which must stay per-task for the locking to be correct).
- board.ts: notifyThreadParticipants ran one usersTable lookup per thread participant on every single board reply. Now batches all participants into one inArray query.
- Verified: tsc --noEmit clean on both files, and the full vitest suite (92 tests across 9 files, including carpools.test.ts and dashboard.test.ts) passes unmodified against these changes.
- No schema/migration changes — pure route logic, drizzle-orm's .for("update") requires no schema change, just a row lock at query time.
